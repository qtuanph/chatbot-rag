# 2.2 — Chat Workflow

Luồng chat hiện tại là **stateless chat** + **structure-aware retrieval**.

## Tóm tắt

```text
Client gửi recent messages
-> backend resolve tenant
-> normalize query (loại bỏ stopword, xử lý dấu câu, giữ nguyên ERP phrase)
-> check Semantic Cache (tenant-isolated)
-> retrieve context theo tenant
-> gọi LLM
-> stream hoặc trả response hoàn chỉnh
```

## Kiến trúc Chat

Toàn bộ hệ thống hiện sử dụng chuẩn OpenAI-Compatible API làm luồng chat duy nhất:

### Chat API Endpoints
- Base API Path: `/v1`
- Route chính:
  - `GET /v1/health`
  - `GET /v1/models`
  - `POST /v1/chat/completions` (Hỗ trợ cả stream và non-stream)
- Phương thức xác thực: Bearer Token (Tenant API Key)
- Các tham số mở rộng: `thinking_mode` (cho phép kích hoạt khả năng suy luận sâu)

## Stateless rule

Backend không lưu transcript bền:

- không restore history
- không có `chat_sessions` / `chat_messages`
- frontend chỉ giữ một cửa sổ message ngắn trong memory

## Retrieval rule

Retrieval phải lọc nghiêm ngặt theo `tenant_id`.

### Query rule

- retrieval mặc định chỉ dùng **latest user query**
- history vẫn được giữ cho LLM context
- history không còn là nguồn RAG expansion mặc định

### Retrieval path

1. normalize query hiện tại (giữ nguyên thuật ngữ ERP, xoá stopword, xử lý dấu câu)
2. **kiểm tra Tier 0 FAQ Cache**: lookup O(1) qua SHA-256 hash của normalized query trong PostgreSQL `escalations` (`status = 'published_faq'`). Nếu hit -> phản hồi tức thì trong **~20ms**, 0 token LLM
3. **kiểm tra Tier 1 Exact Cache & Tier 2 Semantic Cache** (Redis & Qdrant, được chia theo `tenant_id`). Phản hồi rỗng ("Empty Response") được bảo vệ không ghi vào cache
4. nếu query mang dáng heading / numbered section -> ưu tiên section route
5. semantic route luôn truy vấn chunk collection
6. `RecursiveRetriever` mở rộng section -> chunk
7. `AutoMergingRetriever` gộp chunk về parent section khi phù hợp
8. thay sentence hit bằng local window context
9. rerank sau candidate cleanup
10. hydrate full section từ PostgreSQL cho top node nếu cần
11. gọi LLM với **System Prompt chuẩn hóa phản hồi**: *"Rất tiếc, chưa đủ căn cứ trong tài liệu để trả lời câu hỏi này."*
12. khi AI trả lời *"Chưa đủ căn cứ"*, Celery Worker **tự động lưu 1 bản ghi vào bảng `escalations` (`status = 'open'`)** để Admin xem xét duyệt thành FAQ trên Webapp `/admin/faqs`

## Provider rule

| Loại | Mặc định hiện tại |
|---|---|
| Embedding | Docker Model Runner |
| Reranker | NVIDIA NIM |
| LLM | 9Router |

## Response rule

Hỗ trợ cả non-stream và stream thông qua giao thức Server-Sent Events (SSE):
- Định dạng gói dữ liệu (shape) bám sát cấu trúc chuẩn của OpenAI.
- Luồng stream tối ưu hóa cho độ trễ thấp (Time To First Token).
- Ghi nhận đầy đủ metadata, citations và usage thông số trong gói tin phản hồi.

## Feedback rule

- route nội bộ: `POST /v1/chat/feedback`
- frontend gửi:
  - `query_text`
  - `assistant_answer`
  - `citations`
  - `feedback_type`
- backend tự gắn:
  - `tenant_id`
  - `user_id`
  - `llm_model`
  - `embedding_model`
  - `reranker_model`

## Invariants

- mọi chat phải có tenant context (thông qua giải mã API Key hoặc JWT của Tenant Admin)
- các thao tác quản trị trên Next.js Admin Panel đi qua proxy `/api/bep/*` để bảo mật JWT/Token
- tích hợp chatbot Client (Widget ERP, Playground) kết nối trực tiếp đến API Endpoint bằng API Key
- không lưu transcript vào `localStorage`
